# Fleet Phase −1 — 物理 Spike 执行手册

`docs/fleet.md` §8 规定：Fleet 控制面的任何代码开工前，必须先通过这一关。本文件是那张
"开工前必须固定的验证矩阵"，写成可以直接照着做、可以签字的形式。

> **本手册不需要写任何将来要长期维护的代码。** 一次性的采集脚本、抓包工具、临时
> harness 都可以写，而且应该写——否则无法完成验证。禁止的是 server / launcher 的控制面实现。

## 0. 开工前必须先填死的变量

**这一节没填完就不要开始测。** 变量不固定，测出来的数据无法比较，也无法复现。

| 变量 | 值 | 备注 |
|---|---|---|
| 设备型号 | ⬜ | 单一型号，不要混。真机农场的一致性从这里开始 |
| Android 版本 / 安全补丁级别 | ⬜ | |
| 目标 App 及版本 | ⬜ | 每个目标 App 都要记版本号，风控随版本变 |
| 账号样本 | ⬜ | 数量、来源、养号状态。**不要用真实业务账号做检测测试** |

| 网关硬件 / OS / 内核版本 | ⬜ | 跑策略路由那台 |
| 设备数量 | ⬜ | **≥10，目标 20**。5 台暴露不出 AP 空口、USB 供电和 conntrack 的竞争 |

## 1. 门禁项（不通过则整条路线的前提不成立）

### G1 — 目标 App 对 ADB / scrcpy / 受管理设备的检测 🔴 最高优先级

**这是唯一一个"失败就要推翻路线"的测试。先做它。**

必须用**对照组**，不能只测一种配置。"未观察到检测"不等于"未被检测"。

| 组 | USB debugging | scrcpy 运行中 | Device Owner/DPC | 结果 |
|---|---|---|---|---|
| A（基线） | 关 | 无 | 无 | ⬜ |
| B | 开 | 无 | 无 | ⬜ |
| C | 开 | 有 | 无 | ⬜ |
| D | 开 | 有 | 有 | ⬜ |
| E | 关 | 无 | 有 | ⬜ |

每组的观测指标（都要记，不要只看"能不能登录"）：

- 登录成功率、验证码触发率、二次验证触发率
- 账号存活时长（**至少观察 72 小时**，风控常常延迟生效）
- 内容分发量 / 触达异常
- Play Integrity 判定结果（`MEETS_DEVICE_INTEGRITY` 等）

**判据**：若 C/D 组相对 A 组有统计上显著的劣化 ⇒ **G1 失败**。
失败后的选项：改为最小 Agent（放弃 scrcpy 串流，改截图轮询）、或整体重新评估路线。
**不要在 G1 有结论之前写任何控制面代码。**

### G2 — 网络层代理无泄漏

设备上不装 VPN App，全部在网关做。逐项验证并**留抓包文件**：

| 项 | 抓包位置 | 判据 | 结果 |
|---|---|---|---|
| IPv4 TCP | 网关 + 上游出口 | 出口 IP 正确 | ⬜ |
| **IPv6** | 网关 | **无任何绕过代理的 v6 流量**（最常见的泄漏） | ⬜ |
| UDP / QUIC / HTTP3 | 网关 | 要么走代理，要么被明确阻断而非静默直连 | ⬜ |
| STUN / WebRTC | 网关 | 同上 | ⬜ |
| DNS（普通 53） | 网关 | 走指定解析器 | ⬜ |
| **Private DNS (DoT)** | 网关 | 不绕过 | ⬜ |
| **App 自带 DoH** | 网关 | 不绕过 | ⬜ |
| captive portal 检测 | 网关 | 与业务流量同出口 | ⬜ |
| NTP | 网关 | 同上 | ⬜ |
| Google Play 服务 | 网关 | 同上 | ⬜ |

**一致性检查**（App 不需要检测 VPN 就能发现异常）：

- 出口 IP 地理位置 ↔ 设备时区 ↔ 系统语言 ↔ SIM MCC/MNC ↔ GPS：⬜ 全部自洽
- 设备侧看到的是普通 Wi-Fi + 本地 ISP DNS，但公网 IP 是移动/住宅 ASN ⇒ **矛盾，必须消除**：⬜

**判据**：任一泄漏项未封堵 ⇒ G2 失败 ⇒ 退回设备侧 VPN（带 `tun0` 特征，防关联优势打折），需重新评估收益。

### G3 — 代理切换的连接排空

切换流程必须是：force-stop 目标 App → 清理该设备 conntrack zone → 切策略 → 验证出口 → 再启动。

- ⬜ 切换后**旧 TCP 连接确实断开**（抓包确认，不能只看新连接）
- ⬜ 切换后**旧 QUIC 连接确实断开**
- ⬜ conntrack 表中该设备旧条目已清除
- ⬜ 切换不需要重启整台设备

## 2. 可行性项（失败不推翻路线，但要有对策）

### F1 — 恢复出厂后的无人值守重新入池

- ⬜ 恢复出厂 → 重新 enrollment **全程无需人工点屏**
- ⬜ ADB key 重新授权
- ⬜ Wi-Fi 配置重新下发
- ⬜ Device Owner / DPC 重新设置
- ⬜ 证书重新签发
- ⬜ **FRP（恢复出厂保护）流程可控**，不会把设备锁死
- 单台最大 enrollment 时长：⬜ ______ 分钟

### F2 — 物理规模

在**满负荷**（全部设备同时在线 + 串流）下测：

- ⬜ 20 路 USB 同时工作，无掉线
- ⬜ 供电充足（记录满载电流 vs hub 额定）
- ⬜ 温度稳定（记录满载 30 分钟后的机身温度）
- ⬜ AP 空口容量够用（记录吞吐与重传率，2.4/5 GHz 分别测）
- ⬜ conntrack 表容量与透明代理进程无瓶颈
- USB 断连率：⬜ ______ 次 / 24 小时

### F3 — Google 生态

- ⬜ Play 商店可正常安装
- ⬜ Play Integrity 判定结果记录（各对照组分别记）
- ⬜ Google 账号设备数上限的实际影响
- ⬜ Play Protect 是否干预
- ⬜ bootloader 状态对上述各项的影响

## 4. 恢复场景的 pass/fail 判据

| 场景 | 通过条件 | 结果 |
|---|---|---|
| factory-reset | 无人值守回到可用状态，生成**新的 DeviceIncarnation** | ⬜ |
| reboot | 自动重连 Rack Agent，恢复原 assignment | ⬜ |
| 断网恢复 | 重连后**不补执行**断网期间积压的命令（fail-closed，见 `docs/fleet.md` §4.2） | ⬜ |
